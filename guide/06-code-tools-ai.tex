\section{GitHub}\label{app:code:github}
Keep your work in the three GitHub repositories described in \cref{app:start:access}: code, models, notes, drawings, PDFs, presentations and the Overleaf-synced paper. Readers can access code anonymously for double-blind review through \href{https://anonymous.4open.science/}{Anonymous GitHub}, or as a permanent DOI archive through Zenodo (\cref{app:zenodo}).

\paragraph{Repository layout.} Use a top-level notes repository with paper and code submodules. This keeps their histories separate within one clone:
\begin{itemize}[noitemsep]
  \item notes repository: \texttt{README.md} linking the pieces; \texttt{notes/} for notes, drawings and consultation summaries; \texttt{slides/} for presentations;
  \begin{itemize}[noitemsep]
    \item \texttt{paper/}: submodule, the Overleaf-synced paper repository, with the TikZ sources of every figure in \texttt{figures/};
    \item \texttt{code/}: submodule, the code repository: the code in \texttt{src/} and \texttt{tests/}, the measurement scripts and their raw results in \texttt{experiments/}, and at the root \texttt{README.md}, \texttt{LICENSE}, \texttt{.zenodo.json}, \texttt{CITATION.cff}, the \texttt{justfile}, the \texttt{Dockerfile} and \texttt{.devcontainer/}.
  \end{itemize}
\end{itemize}
Zenodo archives only the code repository. Include the code and data behind the paper's results in each release (\cref{app:zenodo}).

\paragraph{One command.} Create the code repository from \href{https://github.com/BlackLight54/tdk-code-template}{tdk-code-template}. It provides the layout above, Zenodo files, Docker images and one GitHub Actions workflow per recipe: \texttt{ci} (build, test and smoke reproduction), \texttt{evaluate}, \texttt{benchmark}, \texttt{robustness}, \texttt{demo} and \texttt{release}.

Put recurring commands in a \texttt{justfile} for the \href{https://github.com/casey/just}{just} command runner. \texttt{just reproduce} must regenerate every paper figure and table. Name individual recipes after their outputs: \texttt{just fig-scalability} for the scalability figure (\cref{fig:guide:scalability}) and \texttt{just tab-robustness} for the robustness table (\cref{tab:guide:robustness}). \texttt{just reproduce} runs them all. Provide \texttt{just reproduce --smoke} with a reduced workload that finishes in minutes. GitHub Actions runs it on every push to catch broken README commands.

\section{Paper CI}\label{app:code:paperci}
The paper repository's \texttt{.github/workflows/paper.yml} builds both PDFs on every push to \texttt{main} and every pull request that is not a draft. It runs each rule in \texttt{scripts/lint.lua} as a separate step. The run page shows each result and annotates findings at the relevant file and line. Each annotation is titled with what is wrong and says what to do, with the text to write instead where the lint knows it. The job summary starts with the essentials (\cref{app:writing:essentials}): a line of marks, then a row per essential. A second table groups the other rules as on the Checks page. There are three rule families; \texttt{texlua scripts/lint.lua list} describes each rule.
\begin{description}[noitemsep]
  \item[source] Checks the sources and build log. Gates cover phase-appropriate essentials (\texttt{essentials}), the template structure (\texttt{frame}), a clean build and an outline matching the spine. They also check floats, captions, axes, tables, labels, references, acronyms, listings, the shape of the reference list, typography, consistent terms, that no TDK paper of the same year is cited or linked (\cref{app:tdk:companion}), headline numbers against the evaluation, and completion of the AI declaration and title page. Burn-down rules for placeholders, beats and a JSON record only report. A rule that cannot run, because a tool is missing or the profile excludes it, says \emph{skipped}, never \emph{pass}.
  \item[pdf] Checks the reviewer PDF against form requirements, even if you replaced the template. Checks cover A4, metadata, embedded fonts, the faculty's 15\,MB limit, and a 12\,pt serif body font identified as Times. They measure single line spacing from line pitch and margins of 1.5--3.5\,cm from the text on every page. They report text below 10\,pt, count main-text pages from the PDF outline, and check required parts, including both abstracts and the AI declaration. For a thesis, \texttt{LINT\_PROFILE=thesis} applies the faculty's thesis thresholds.
  \item[tools] Reports from TeX Live and container tools: chktex and lacheck for typography, texcount for chapter word counts and abstract length, checkcites for uncited reading-list entries, the BibTeX log, hunspell for unknown words, and a link check. These do not block the build.
\end{description}
Each rule has a \emph{severity} and a \emph{phase}. A \emph{check} fails the run, \emph{advice} warns, and a \emph{count} reports numbers. Checks become required at \texttt{draft}, \texttt{polish} or \texttt{submit}; before then, they only report. Set your phase in \texttt{thesis.tex} as work progresses: \texttt{topic}, \texttt{setup}, \texttt{research}, \texttt{plan}, \texttt{draft}, \texttt{polish} or \texttt{submit}, the phases of the lifecycle. The first four share the checks' first level, and the lint rejects any other value. Page count blocks only on \texttt{main}, so a branch may be short while you draft a chapter. \texttt{texlua scripts/lint.lua list} shows each rule's severity and phase. The same lint generates the draft's \emph{Checks} page on every compile (\cref{app:latex:todo}), keeping the PDF and CI consistent.

The workflow is part of the Overleaf template and is copied into each new student project. Overleaf's GitHub sync creates the student's repository; its first push starts CI. View runs under GitHub's \emph{Actions} tab or on a pull request.
\paragraph{Lifecycle CI.} The notes repository from \href{https://github.com/BlackLight54/tdk-notes-template}{tdk-notes-template} has a separate workflow. Every push and Monday morning, it regenerates \texttt{lifecycle.md} with file-based checks. It checks that the three anchors in \texttt{notes/anchors/} are longer than stubs, counts summaries in \texttt{notes/consultations/}, and checks that submodules have moved within two weeks. It also checks for the code README, licence, justfile, tests, Dockerfile and Zenodo file, and requires slides before the conference. Due phases come from the paper's \texttt{\textbackslash lintphase}.

The workflow appends the paper's burn-down counts to \texttt{burndown.csv}, plots \texttt{burndown.svg} and commits both for consultation use. These checks inventory the work; we still assess its quality.

\paragraph{Self-score and reviewer passes.} The paper repository carries two agent skills in \path{.claude/skills/}, so each commit has the skills that review it. On every push, paper CI uploads the evidence of that commit as one artifact: both PDFs, the build logs, the lint output and the skim view, kept for 14 days. \path{.claude/skills/self-score/} scores the artifact's \texttt{reviewer.pdf} A--E using the review sheet's wording and page references, and identifies the weakest criterion and cheapest fix. \path{.claude/skills/reviewer-passes/} runs the skim reviewer and expert panel on the same artifact. \texttt{scripts/review/review.py} fetches the artifact of a named commit and checks its hashes. Self-score writes nothing; the reviewer passes write nothing unless you record a run. See \cref{app:lifecycle:reviewers} for when and how to use the panel.

\section{The README}\label{app:code:readme}
Every TDK needs a \emph{results} repository that lets reviewers reproduce its numbers. Some also produce a reusable \emph{tool}. The code template's \texttt{README.md} starts with the results sections. Extra tool sections appear in a commented block below: delete the block for results only, or uncomment it for a tool.

\paragraph{The results README.} In this order:
\begin{enumerate}[noitemsep]
  \item What this is, in two sentences, with the paper's title and the concept DOI badge (\cref{app:zenodo}).
  \item The reproduction command: \texttt{docker run \dots{} reproduce} for every figure and table (\cref{app:code:docker}). Follow it with \texttt{just reproduce} for local clones and a list of pinned dependencies. Keep dependencies to a minimum.
  \item A results map with one row per paper figure and table: its number, reproduction command, output path and wall-clock time on specified hardware.
  \item Reproduction limits: secrets, special hardware, long runs or nondeterminism, including the seed policy and expected variance. Keep this section even if everything reproduces with fixed seeds.
  \item The results tag: which Git tag and Zenodo version the paper's numbers came from (\cref{app:zenodo:versions}).
  \item How to cite, and the license.
\end{enumerate}

\paragraph{The tool README} adds installation, use on the reader's own input with a worked example, contribution instructions and maintainers after the results sections. Follow the conventions of the open-source foundations we work with, such as \href{https://github.com/LF-Decentralized-Trust/lab-proposals/blob/main/README.md}{LF Decentralized Trust Labs}: an Apache 2.0 \texttt{LICENSE}, a \href{https://developercertificate.org/}{Developer Certificate of Origin} sign-off on every commit (\texttt{git commit -s}), \texttt{MAINTAINERS.md} and a \texttt{SECURITY.md} with vulnerability-reporting instructions. A compliant tool can be proposed as a lab after the TDK.

\section{Docker}\label{app:code:docker}
Make \texttt{docker run} the simplest way to reproduce results. We assume a computer science reviewer has Docker; see Docker's \href{https://docs.docker.com/get-started/}{Get started} if you are new to it. The code template provides two images:
\begin{itemize}[noitemsep]
  \item The \textbf{runtime image} is built by the root \texttt{Dockerfile}, with \texttt{just} as its entry point. Run \texttt{docker run --rm -v \$PWD/out:/out ghcr.io/<you>/<repo> reproduce} to regenerate all results into \texttt{out/}, or \texttt{\dots{} fig-scalability} for one figure. Pin every dependency to make the environment independent of the reviewer's machine.
  \item The \textbf{development image} includes the toolchain, language servers and test runner. Its \texttt{.devcontainer/devcontainer.json} follows the open \href{https://containers.dev/}{Development Containers} specification. VS Code, GitHub Codespaces and Docker's development environment feature can open the repository ready for work. We use the same environment when helping you.
\end{itemize}
A \href{https://docs.github.com/en/actions}{GitHub Actions} workflow builds both images on every push and publishes the runtime image to the \href{https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry}{GitHub Container Registry} on each release. Use the same tag for the image and Zenodo version. The README's first command must select the results-tag image.

\section{Demos}\label{app:code:demo}
Record demonstrations with a script in the code repository, never by hand. A script lets you update the recording after code changes and rerun it before a talk. Have CI publish a fresh recording on every push for the README, talk and reviewers.
\begin{itemize}[noitemsep]
  \item For a web UI, use \href{https://playwright.dev/}{Playwright} to drive the real workflow and save a video and trace. Draw captions into the frames at each step.
  \item For a backend, CLI or prover such as Tamarin, Lean or a model checker, record a scripted terminal session with \href{https://asciinema.org/}{asciinema}. Render it to SVG or GIF, or embed the cast beside the verdicts in HTML. We use this for our backends and proof assistants.
\end{itemize}
Use captions to explain the invariant, rejected attack or result in the running example's terms. Do more than narrate clicks. The code template includes a recorder in \texttt{demo/} and a \texttt{demo} workflow that uploads its recording as an artifact. Run it locally with \texttt{just demo}.

\section{Behaviour-driven tests}
For behaviour-driven development (BDD), write the expected behaviour as scenarios with \href{https://cucumber.io/}{Cucumber}; the scenarios then double as evaluation cases that a reviewer can read.

\section{AI tools}\label{app:code:ai}
\paragraph{Disclose.} For both TDK papers and theses, complete the faculty's AI declaration (\tplref{aidecl}, after the bibliography) and cite AI-generated facts as described in \cref{app:writing:ai}.

\paragraph{Keep every conversation.} Save every AI conversation about the work. Do not use temporary or incognito chats. The declaration needs the essential part of each prompt; an AI citation needs its date and a link. Transcripts also let you recover decisions, arguments and text. Check that your tools retain them, and do not delete them.
\begin{itemize}[noitemsep]
  \item Claude Code keeps every session as a transcript under \path{~/.claude/projects/}, one file per session; Codex keeps them under \path{~/.codex/sessions/}.
  \item ChatGPT and Claude on the web keep conversations in your account history; create a share link for any conversation you cite.
  \item Other tools: check where they store history, and export it regularly if they do not keep it.
\end{itemize}
These transcripts can contain everything you pasted in, so keep them out of public repositories.

\paragraph{Do not wipe your machine.} Retained histories let you reconstruct the declaration and earlier decisions. During the TDK, avoid reinstalling the operating system or clearing your home directory. If necessary, first back up \path{~/.claude/}, \path{~/.codex/}, \path{~/.t3/} and any other tool histories, then restore them afterwards.

\paragraph{Tools, as of October 2026.} These recommendations can become outdated within months.
\begin{itemize}
  \item Use the strongest models for research. We prefer Claude Fable and ChatGPT Astra; ask whether we can help with a subscription.
  \item Prefer an agent working in your repository: Claude Code or Codex, ideally through T3 Code, GitKraken Kepler or herdr. This gives the agent access to your files and its repository tools. You \emph{need} version control when AI edits files.
  \item For productivity, try the Matt Pocock and poetato plugins; for token savings, caveman, ponytail, squeez and TRON. We recommend the \href{https://www.aihero.dev/skills-grill-me}{grill-me skill} (\href{https://claudemarketplaces.com/skills/mattpocock/skills/grill-me}{marketplace page}); see also \href{https://github.com/cursor/plugins/blob/main/pstack/skills/unslop/SKILL.md}{unslop} and \href{https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md}{ponytail}.
  \item Keep instructions concise. Overloaded \texttt{AGENTS.md} files and memories can impair model performance. Prefer skills that clearly describe the range of tasks they apply to.
\end{itemize}
